# AGENTS.md

Guidance for AI coding agents working on this repository, or integrating this engine into another project.
Human-facing documentation lives in [README.md](README.md).

## What this is

A headless SameGame engine in TypeScript. It owns the board state and the rules
(region detection, removal, gravity, compaction, refill) and returns a description
of every change, so any renderer can animate it. It contains no rendering code
and has no runtime dependencies.

## Layout

```
src/SameGame.ts       engine: board state, rules, change tracking (public API)
src/FloodFill2D.ts    generic, stateless flood fill used by SameGame
examples/             browser demos (DOM only), one module per scene in examples/scenes/
examples/demo.ts      demo shell: loads scenes dynamically, exposes setDescription/setLog globals
examples/globals.d.ts type declarations for those globals
public/               static files copied into docs/ at build time (llms.txt)
docs/                 built demo, served by GitHub Pages — generated by npm run build, never edit by hand
```

The library is distributed by copying `src/SameGame.ts` and `src/FloodFill2D.ts`
into a project, not through npm (`package.json` is `private`). Both files must stay
self-contained: no imports beyond each other.

## Commands

```
npm ci                install dev dependencies (TypeScript, Vite) from the lock file
npm run dev           start Vite and open the examples
npx tsc               typecheck src/ and examples/
npm run build         typecheck, then build the demo into docs/
```

There is no test suite. To verify a change, run `npx tsc`, then exercise the engine
with a small script or through the examples (`npm run dev`). Run `npm run build` and commit
`docs/` only when the published demo should change.

## Rules for changes to the engine

- Stay headless: no DOM, canvas, timers, frameworks or rendering concepts in `src/`.
- Keep the tile type generic (`T`). Never assume tiles are numbers or strings.
- Every operation that is part of a move must be reported in the returned
  `SameGameBoardChange<T>`. If you add a new kind of board change, add a new array
  to the change object rather than overloading an existing one.
- Keep behavior deterministic for a given generator. The only internal randomness is
  in `generatePlayableBoard` (used when `ensurePlayable` is true), which calls
  `Math.random()` directly; don't add more.
- Don't change the meaning or order of existing change arrays: renderers depend on it
  (see "Change model" below).
- When the public API changes, update the API Overview and Types sections of README.md
  and the corresponding parts of this file.

## Code style

Match the existing code:

- 4-space indentation, single quotes, semicolons
- explicit type annotations on locals and loop counters (`let row: number = 0`)
- `import type` for type-only imports (`verbatimModuleSyntax` is on)
- braces on every block, `else` on its own line
- lower-case JSDoc comments on every method, describing parameters and return values
- `strict`, `noUnusedLocals` and `noUnusedParameters` are enabled

## Engine semantics

### Coordinates and grid

- Positions are `{ row, col }`. Row 0 is the top row, column 0 the leftmost column.
- `getGrid()` returns the internal `(T | null)[][]` indexed `grid[row][col]`; `null` is an
  empty cell. It is the live array, not a copy: read it, never mutate it directly
  (use `setTile`).
- There is no `getRows()` / `getCols()`; use `getGrid().length` and `getGrid()[0].length`.
  Both swap after a rotation.
- `FloodFill2D` uses `{ x, y }` (x = column, y = row). `SameGame` converts to `{ row, col }`
  at the boundary; don't leak `Point` into the public `SameGame` API.

### Regions and the comparator

- Regions are orthogonally connected (4 directions). A region needs at least 2 tiles to be
  removable.
- The comparator is called with `T | null`, including `null` for empty cells. With object
  tiles it must handle `null` explicitly:
  `(a, b) => a !== null && b !== null && a.type === b.type`.
- The default comparator is `===`, which for object tiles compares references, so every
  freshly generated object would be its own region. Object tiles need a comparator.

### Change model

`removeRegion(row, col)` returns `{ removed, moved, shifted, spawned }`. If the region has
fewer than 2 tiles, all four arrays are empty and the board is untouched.

The phases happen in this order, and each phase starts from the board left by the previous one:

1. `removed`: the region's cells are cleared (`at`, `value`). Order follows the flood fill,
   not reading order.
2. `moved`: gravity. `from` is the position on the board after removal.
3. `shifted`: normal mode only. Empty columns (gravity `down`/`up`) are compacted toward
   column 0; empty rows (gravity `left`/`right`) are compacted toward row 0.
   `from` is the position **after gravity**.
4. `spawned`: endless mode only. Every empty cell is refilled, in row-major order. There
   is no compaction in endless mode.

A tile can appear in both `moved` and `shifted`: it first falls, then its column slides.
For example, `moved: (0,1) → (1,1)` followed by `shifted: (1,1) → (1,0)`.
Renderers must therefore apply the phases in sequence, not merge them by position.

### Mutations that return no change object

These modify the board but return `void`, so a renderer must resync from `getGrid()`
afterwards: `setTile`, `randomize`, `generatePlayableBoard`, `rotateClockwise`,
`rotateCounterClockwise`, and `setGravity(gravity, true)` (which applies gravity and,
in normal mode, compaction immediately).

`setMode` takes effect from the next `removeRegion` call; it does not refill or compact.

### Other details

- `hasMoves()` is true when any tile has an equal orthogonal neighbor.
- `getAllRegions()` returns only removable regions (size ≥ 2).
- `getBoardStats()` recomputes all regions on every call; avoid calling it every frame.
- `randomize(generator)` also replaces the generator used for refills.
- `getAllTiles()` returns every non-null tile value in row-major order.

## Integrating the engine into a game

Typical renderer loop:

1. Create the board and draw one sprite per non-null cell of `getGrid()`, keeping a
   `sprites[row][col]` lookup.
2. On click, call `removeRegion(row, col)`. If `removed` is empty, ignore the click.
3. Animate `removed` (destroy or fade those sprites), then `moved`, then `shifted`, then
   `spawned`, updating the sprite lookup after each phase so the next phase's `from`
   positions resolve to the right sprites.
4. After the animations, check `hasMoves()` (normal mode) to detect the end of the game.
5. Block input while animations run, and resync from `getGrid()` after any of the
   `void` mutations listed above.

Scoring, levels, timers and input handling belong in the game, not in the engine.
